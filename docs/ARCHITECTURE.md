# Архитектура: проверяем среду, а не обучаем модель

## Два слоя

`support-preflight` — независимый устанавливаемый пакет среды. В нём бизнес-переходы,
синтетические задачи и настоящий адаптер Verifiers v1. Он не зависит от X-Ray.

`xray` — нейтральный потребитель JSONL. Сканеру не нужен доступ к модели или банковским
системам. Только команде `demo --live` нужны API и Verifiers.

Нативный `eval` создаёт Taskset → Task → отдельный MCP Toolset на каждый rollout.
Встроенный `null` harness вызывает модель. Модель предлагает действие; инструмент
изменяет состояние; deterministic verifier проверяет результат. Typed V1 State хранит
переходы, `finalize` передаёт их в trace.info. Экспортёр извлекает только структурированные
события и token usage. Длинные рассуждения модели не нужны для X-Ray.

## Три идентичности состояния

- `internal_state` — полный снимок, включая hidden, milestones, turn и accumulated_reward.
- `state_id` — SHA-256 префикс канонического internal business state без двух счётчиков
  turn/accumulated_reward. Hidden, paid milestones и terminal **сохраняются**.
- `observable_state_id` — идентичность snapshot, доступного агенту. Нужна для сравнения
  одинаковых наблюдений при разных скрытых причинах.

Если включить monotonically increasing turn в идентичность, граф конечного эпизода
станет DAG: ни один узел не повторится. Поэтому цикл в отчёте — цикл **бизнес-состояния**,
а не полное возвращение часов назад. Лимит 16 действий ограничивает выигрыш. Мы показываем
не бесконечный доход, а положительную награду за отсутствие нового бизнес-прогресса.

## Верификация против reward

`business_success` всегда означает refund completed + customer notified + ticket resolved.
В broken rubric достаточно resolved. Поэтому агент может получить +1 и плохой бизнес-исход.
В fixed это закрытие запрещено. Milestone reward может быть положительным до завершения
задачи: это намеренная промежуточная обратная связь, а не success label.
В fixed итоговый `@vf.reward` для training равен binary business success. Сумма milestone
feedback остаётся отдельной метрикой. Иначе остановка сразу после уведомления могла бы
получить ту же награду, что и корректное закрытие. В broken training reward намеренно
равен сумме дефектного feedback.

Финальный guard добавлен после live eval и проверен offline regrading сохранённых model
trajectories: все они успешны, поэтому численные оценки не изменились. Tool schemas,
prompt, transitions и feedback, которые видела модель, при этом не менялись. Это не новый
model rollout; отдельный regression test проверяет нулевой score при остановке до closure.

Approval — детерминированный синтетический сервис. Escalation сразу даёт approved.
Нет финансовой операции, реального оператора, IAM/RBAC, CRM или гарантии безопасности MCP.

## Что измеряется

1. SCC ограничивает кандидатов на циклы. Проверка ищет фактически наблюдённые непрерывные
   замкнутые пути с положительной суммой, не склеивает эпизоды в мнимый exploit.
2. Goal/reward mismatch сравнивает независимый бизнес-результат и rubric success.
3. Consistency сравнивает одинаковые observed snapshot/action/args. Последний шаг,
   обрезанный известным turn cap, не используется как свидетельство скрытого бизнеса.
4. History association группирует предыдущие действия. Наблюдательная ассоциация — не
   доказательство причинности, не автоматический вывод «среда не Марковская».
5. Reachability: наблюдённый successful path — свидетельство существования этого пути.
   Отсутствие пути в выборке — unknown. Отдельная функция для exhaustive reference graph
   протестирована на невозможном target; на support demo глобальный verdict не применяется.
6. Coverage — число состояний, переходов, действий и эпизодов. Знаменатель пространства
   неизвестен, процента полного покрытия нет.

## Gate и health

За каждый уникальный CRITICAL-код: −30; WARNING: −8; INFO: 0. Минимум 0, максимум 100.
Есть critical → FAIL / DO NOT TRAIN / exit 1. Только warnings → REVIEW / exit 2.
Нет findings → PASS / exit 0 в рамках предоставленной выборки. Невалидный/пустой вход →
ошибка, не PASS. Это продуктовая эвристика; **100 — не вероятность безопасности**.
Hodge-style residual не влияет на score или gate.

## Воспроизводимость и ограничения

Одинаковые scenario rows, prompt, model, temperature, лимит и scripted probes для обеих
версий. Ответы модели не обязаны совпадать даже при temperature 0: это matched tasks,
не идентичные trajectories. API стоимость не получена → `null`, не «бесплатно».
429 повторяется с backoff внутри одного запроса; это не новый эпизод и не скрытая смена модели.
Пробы явно помечены `scripted_probe`, model-only отчёты сохранены отдельно.

Последовательность вызовов должна быть сериализована: V1 state sync делает read/modify/write.
Поддержку параллельных мутаций нужно тестировать отдельно; этот demo просит один tool за раз.
Нет RL training и нет доказательства того, чему обучится новая policy после обучения.

## Для product MVP дальше

Нужны явные требования к suite coverage, переход от «нет найденных дефектов» к политике
приёмки заказчика, adapters к другим агентным runtime, автоматические mutation/probe suites,
контроль доверия к самому business verifier и тесты replay на реальных интеграциях.
